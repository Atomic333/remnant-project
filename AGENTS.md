- Every Quest Coin earn goes through `awardByRule` in `supabase/functions/_shared/quest.ts` with a unique `award_key`; purchases, refunds and adjustments run only through the service-role database functions (`purchase_item`, `refund_redemption`, `admin_adjust`). Why: one place enforces idempotency, limits and non-negative balances.
- H5P packages are unpacked by the `h5p` edge function into the private `h5p-content` bucket and served through that function's `/file/<activityId>/...` path; completions pay only via server-started attempts in `h5p_attempts`. Why: keeps files private-bucketed and rewards server-checked.
- Imported research collections live in staging tables (`collections`, `collection_markers`, `collection_sources`, `collection_images`, `import_issues`), separate from `markers`, and stay `draft`; visitors can only read `published` rows and cleared images. Why: markers requires city/coords, and drafts must never leak or pay coins.
- Home is a d3-geo SVG globe (`src/components/globe/`), lazy-loaded; city cards deep-link to `/map?city=&lat=&lng=&z=`. Why: no WebGL keeps phones fast, and collection-only cities have no curated center.
- Collection stories go live only through `set_collection_status` (a trigger also blocks publishing unready rows); the main map shows published, non-withheld stories as a separate pin layer. Why: readiness checked server-side, `markers` untouched.
- Published collection stories adapt into shared marker features at visitor boundaries, while drafts and withheld coordinates remain collection-only. Why: feature parity without leaking research drafts or making protected locations routable.
- Generated H5P activities store only `h5p.json` + `content/content.json` in `h5p-content` and load libraries from `public/h5p-libraries/` (flag `generated`); library `dist/` folders are renamed `bundle/` because `dist` is git-ignored. Why: one shared library copy, and generated rows can be replaced without touching uploads.
